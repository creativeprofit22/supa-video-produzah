# 0002 — Graphics render with fframes in a separate sidecar

Animated graphics (titles, lower-thirds, later maps and charts) need a real 2D engine with keyframed motion, which FFmpeg filter graphs do not give us. We use fframes at the pinned commit `7bbec1278c7687ac43f88524d9b149a31b7cfdf6` (v1.1.0), built as its own program, `supa-graphics-render`, from `apps/desktop/src-tauri/graphics-renderer/`. That crate has its own `[workspace]` and `Cargo.lock`, and the Tauri app does not depend on it. The app runs the renderer like FFmpeg: through `run_supervised`, with cancellation that kills the process. The renderer writes transparent RGBA PNG frames. Our pinned FFmpeg 8.1.2 sidecar then encodes them as QuickTime Animation (`qtrle`, `argb`) in a `.mov`, the _graphics overlay clip_. The export path composites that clip like any other top video input, so the render plan did not change. `qtrle` and the `mov` muxer were added to the media-toolchain manifest's required capabilities; the bundled build already had both.

Even if we only render frames, fframes still depends on `fframes-media` → `ffmpeg-sys-fframes`. So the build needs FFmpeg 9 libav as shared libraries and LLVM/libclang for bindgen. `scripts/bootstrap-graphics-renderer-windows.ps1` fetches a pinned BtbN FFmpeg 9.0.2 win64 GPL shared build (SHA-256 checked) into `.cache/ffmpeg9-shared/`. LLVM is a system install (on this machine `E:\Tools\LLVM`). `dumpbin /dependents` shows the release executable still imports `avcodec-63`, `avformat-63`, `avutil-61`, `swresample-7` and `swscale-10`, even though it never calls them; it also needs the MSVC runtime (`MSVCP140`, `VCRUNTIME140`). The crate's `build.rs` copies the FFmpeg 9 DLLs next to the executable, so the renderer folder runs without PATH changes. Bundling that folder into the installer is phase 15 work.

The input is a versioned JSON _graphics description_. It is parsed with `deny_unknown_fields` and bounded: canvas ≤ 4096 with even sides, ≤ 240 fps, ≤ 36 000 frames, ≤ 64 layers, text ≤ 500 characters, and one absolute `.ttf`/`.otf` font with no system font lookup. Invalid input exits with code 2. fframes fixes `FPS/WIDTH/HEIGHT` at compile time. We render at the description's canvas size and evaluate keyframes on a fixed 30-per-second index base, so motion is exact at any output rate. Children of the `svgr!` tree are built at runtime, so dynamic layer lists work with `compile-time-svgtree`.

Backends are `auto|gpu|cpu`. `auto` is the default: it tries Skia on Vulkan and falls back to tiny-skia when Vulkan cannot initialise or the first GPU frame fails, and the summary reports which backend ran. On a GTX 1080 the GPU took 13.6 s against 40.5 s on the CPU for 10 s of 1080×1920 at 30 fps (`docs/benchmarks/graphics-render.md`). Renders are deterministic on a given backend. GPU and CPU differ only in edge antialiasing (≤ 0.08 % of pixels). So the reference frames are CPU renders, and GPU output is checked against them with an edge-pixel budget.

Rejected: encoding through fframes' own libav path, because it would add a second, unpinned encoder toolchain next to the hashed FFmpeg sidecar. Also rejected: linking fframes into the Tauri crate, which would put FFmpeg 9 DLLs and libclang into every app build, the Linux CI job and cargo-audit, and would let a GPU driver crash take the app down with it. PNG-in-MOV and ProRes 4444 were not needed, because `qtrle` is lossless, carries alpha and is in the pinned build.
